Hardware Habits That Made Me a Better Software Engineer

December 30, 2025 · 4 min read · hardware · embedded · craft

I started doing embedded projects in school — Arduino, Raspberry Pi, the occasional KiCad board. I figured the skills would mostly stay separate from the web work I was doing on the side. They didn't. The mindset of working with hardware turned out to fix bad habits I didn't even know I had as a software developer.

Five things hardware taught me that I now use every day in backend code:

1. Resources are not free

On a microcontroller you have maybe 32 KB of RAM. You can't just allocate a 10MB array because you forgot to clean it up — there isn't a 10MB array to allocate. You think about memory before you write. You free things deliberately.

In high-level languages it's easy to forget that any of this exists. Then your Node.js process eats 4GB and crashes the server, and suddenly you wish you'd been careful. Hardware made me ask, on every chunk of code: how big does this get? Does it grow forever? When does it get released?

2. There's no "just retry"

If your sensor read fails, you can't pop a toast and ask the user to refresh. You handle it now or the system fails. Web developers reach for retries reflexively — sometimes that's right, often it's hiding a bug that should be fixed at the source. Hardware forces you to think about what should happen when this never works, not just what should happen when this eventually works.

Retries are a wonderful tool. They're also a wonderful place to bury problems.

3. Read the datasheet

If you're using a sensor, the datasheet has the answer. Not a Stack Overflow post. Not a YouTube tutorial. The actual document the manufacturer wrote, with timing diagrams and edge cases nobody has bothered to blog about. It's boring. It's also the truth.

Software has datasheets too — they're called specs, RFCs, and source code. When I'm stuck on a library now, I open the source instead of searching. The answer is usually there in five minutes. The blog post that doesn't quite match my version would have taken an hour.

4. Test in the real environment, not the simulator

Code that works on the breadboard at room temperature doesn't always work in a hot enclosure with a noisy power supply. Embedded engineers test where the thing will actually live. Software engineers — me included — used to skip that step and trust the unit tests on my MacBook.

Now I deploy to staging environments that look like production: same OS, same database version, same network conditions. The bugs that hide in your laptop's perfect environment are the bugs your users are going to hit.

5. If it's not deterministic, you don't understand it yet

An LED that lights up "sometimes" is a bug, not a feature. Either it always lights when the conditions are met, or you don't actually know the conditions. Hardware is unforgiving about this. You can't ship "works most of the time."

I now treat flaky tests, intermittent timeouts, and "weird, it worked yesterday" the same way. Those are signals that a model in my head is wrong, not problems to retry past. Find the determinism. The bug is hiding in whatever assumption is failing intermittently.

The real lesson

Software is forgiving in ways hardware isn't. You can leak memory and the OS will probably clean it up. You can ship buggy code and patch it tomorrow. You can wave at a flaky test and merge anyway. Hardware doesn't let you do any of those things, and developing under those constraints — even briefly — calibrates your sense of "good enough" upward.

I write web backends now, not firmware. But the discipline carries. Production code that handles real money, real people, and real data deserves the same care a sensor on a board does. Both will fail in front of a user who cannot retry.
