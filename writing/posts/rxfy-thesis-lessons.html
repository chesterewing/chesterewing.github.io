What RxFY Taught Me About Shipping Real Software

February 8, 2026 · 6 min read · thesis · rxfy · lessons

RxFY was my thesis: a web-based monitoring and notification system for antibiotic purchases. The pitch was that drug stores in the area didn't have a fast way to spot suspicious buying patterns — high volumes from a single buyer, repeat purchases inside narrow windows, the kind of thing that suggests stockpiling or off-prescription use. We built a tool that watched the sales feed and pinged when something looked off.

The grade went well. The system worked. But the thing I actually took away from it — the thing that still shapes how I write code today — wasn't on the rubric.

1. The first design is always wrong

Our first schema had one big transactions table with a column for everything. Drug name, quantity, buyer ID, date, time, store, prescription number, notes — all in one row. It felt simple. Until we started writing the alert queries and realized we needed to join transactions against a buyer-history rollup, against a drug-controlled-list, against per-store thresholds. The queries got ugly fast. The "simple" schema was making everything harder.

We rewrote it three weeks in. Split into proper tables, added foreign keys, indexed the right columns. Lost a week. Saved a month.

If you're afraid of the schema rewrite, you're going to lose more time avoiding it than doing it.

2. The hardest bug isn't in the code

Halfway through testing, alerts started firing for transactions that didn't exist. We chased it for two days. Looked at the alert engine. Looked at the database. Wrote test cases. Couldn't reproduce it.

It was the system clock. The test machine had drifted by about 40 minutes, so when we logged a transaction "now" and the alert engine queried "everything in the last hour," the engine thought transactions in the future had already happened. The alert engine was right. The clocks were wrong.

This is the lesson: when something doesn't make sense, don't keep looking at the code. Look at the assumptions. Time, timezones, encodings, network reachability, file permissions, environment variables — the bug is often in the layer you didn't think to question.

3. Real users will break it in ways you didn't imagine

We tested with sample data. Real drug stores typed product names with inconsistent spacing, capitalization, and abbreviations. "AMOXICILLIN 500MG" / "amoxicillin 500 mg" / "Amox 500" all referred to the same drug, and our exact-match logic was treating them as three different products. Alerts that should have fired didn't. Alerts that shouldn't have, did.

The fix was a normalization layer — strip whitespace, lowercase, fuzzy-match against a canonical drug list. Boring code. Critical code. The kind of code I now write first instead of last.

4. Documentation is the project

Halfway through, my teammate got sick for a week. I tried to pick up the part of the system she'd been working on and immediately got stuck because nothing was documented. Variable names made sense to her, not to me. Decision rationales lived in chat messages I'd already lost.

We started writing things down — short README files inside each folder explaining what it did, why we chose this library over that one, what the gotchas were. It felt slow at the time. By the final defense it was the most useful thing we'd built. The panel asked questions and we had real answers because we'd written them down for ourselves.

5. The system that ships is better than the system that's perfect

We had a list of features that didn't make it: SMS notifications, multi-store admin dashboard, machine-learning-based anomaly detection (yes, we considered it). Cutting them was painful at the time. Looking back, every cut was correct. The version that shipped was small enough to actually finish, polish, and demo. A bigger system would have been half-broken in three more places.

You can't iterate on what you didn't ship.

What I take with me now

The technical skills from RxFY transferred directly to my current backend role at RocketServe. But the lessons above — design will change, bugs aren't where you think, real users break things, write things down, ship — those are the ones I quote at myself almost daily. Thesis was practice. Production is just thesis with consequences.

If you're still in school working on a capstone or a final-year project: treat it like real work. The grade matters less than the habits you build doing it. Those habits compound for years.
