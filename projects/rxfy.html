RxFY — Antibiotic Monitoring System

Real-time monitoring & notification platform that helps drug stores track antibiotic purchases and flag suspicious patterns automatically.

3 moBuild duration
200+Commits
4Team members
2Pilot drug stores

The Problem

Drug stores in our area didn't have a fast way to spot suspicious antibiotic-buying patterns. High volumes from a single buyer, repeat purchases inside narrow time windows, off-prescription dispensing — all the things that suggest stockpiling or misuse — were buried in paper logs nobody had time to review.

Antibiotic misuse drives resistance. The slow loop between "purchase happens" and "pharmacist notices the pattern" made the problem worse. We wanted to close that loop down to seconds.

Goals

  • Real-time logging of every antibiotic purchase
  • Automatic alerts when patterns cross configurable thresholds
  • Audit trail satisfying public-health compliance requirements
  • Web-based — runs on whatever device the pharmacist already has
  • Simple enough for non-technical staff to operate daily

Architecture

Pharmacists log a purchase in the browser. The PHP front-end forwards it to the Node.js alert engine which checks thresholds against the buyer's history in MySQL. If anything looks off, an alert fires immediately and the audit log is updated regardless.

Tech Stack

  • PHP
  • Node.js
  • MySQL
  • JavaScript
  • Bootstrap
  • jQuery

Key Decisions

  1. Web app, not native. Pharmacies already had a browser open all day. Native would have meant install + IT + training. Web meant "open this URL."
  2. Configurable thresholds, not hardcoded. Every store has different normal volumes. We let admins tune the alert rules instead of guessing for them.
  3. Normalized drug-name lookup. Real users typed "AMOXICILLIN 500MG" / "amox 500" / "amoxicillin 500 mg" interchangeably. We added a fuzzy-match layer before the alert engine even saw the data.
  4. Alerts are best-effort, audit log is not. If the alert engine hiccupped, we still wrote the audit row. Compliance came first; nudges came second.

Lessons Learned

  • Schema rewrites are cheaper than they feel. Our first "simple" schema lost us a week. Refactoring it cost a week and saved a month.
  • The bug isn't always in the code. Spent two days chasing phantom alerts that turned out to be a 40-minute clock drift on the test machine.
  • Real users break things in unimagined ways. Sample data hid the messy-input problem entirely. Pilot data exposed it day one.
  • Documentation is the project. Once we started writing things down, onboarding teammates went from "spend 2 hours guessing" to "read the README."
  • Ship the smaller version. SMS notifications, ML anomaly detection, multi-store admin dashboard — all cut. Each cut was correct.

Outcome

Defended successfully in 2024. Two pilot drug stores ran the system through their normal workflow and the alert engine caught patterns that would have been invisible in paper logs. The system isn't currently deployed beyond the pilot — but the engineering lessons it taught me still shape how I approach every backend project today, including the one I'm now building at Cebuanas.

This was the project that turned "I want to build software" into "I can build software."
